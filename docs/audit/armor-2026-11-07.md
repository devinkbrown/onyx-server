# Armor security and feature audit (2026-11-07)

This audit covers Armor, the pure-Zig TLS and crypto stack, at source revision
`483bfb80`, which is the 0.10.4 image running on both production nodes. It was
read-only.

Seven independent adversarial reviews covered seven slices:

1. TLS 1.3 server
2. TLS 1.2 server and client
3. Record layer, AEAD, key schedule, key exchange, RNG and kTLS
4. X.509, OCSP, signature verification and the outbound TLS client
5. QUIC-TLS, Retry, HPKE and ECH
6. Signature primitives and the `armor` CLI
7. Feature, assurance and documentation inventory

Every security finding below was rechecked against source before it was
included. Candidates that were unreachable or already mitigated were dropped.

## Verdict

The core TLS engines are in good shape. No reachable defect was found in:

- the TLS 1.3 or TLS 1.2 handshake state machines;
- the key schedule, record protection or nonce handling;
- X.509 chain validation, PKCS#1 or PSS verification, OCSP, or hostname
  matching;
- the kTLS key installation path.

Many earlier hardening passes show in the code: GAP-K regression tests, an
exploit corpus, constant-time depadding and binder checks, sequence-wrap
refusal, and duplicate-extension bitsets.

The real problems sit at the edges:

- one pre-authentication memory exhaustion in the QUIC/WebTransport handshake;
- a post-quantum key exchange that is implemented but rarely selected;
- a test corpus that does not cover the production record path;
- several engine features that the daemon never wires up.

## Verified security findings

| ID | Severity | Finding | Location |
|---|---|---|---|
| A1 | **High** | **Unbounded QUIC handshake buffering before authentication.** `quic_conn.pumpCryptoToHandshake` feeds every in-order CRYPTO byte into `quic_handshake.Server.recv` with no cap. `parseHandshakeMaybe` waits for a declared 24-bit length of up to 16 MiB. The 64 KiB `CryptoStream` cap only bounds out-of-order gaps. With 256 allowed connections, an unauthenticated peer can pin about 4 GiB on UDP 4433. | `src/proto/quic_handshake.zig` `feedCrypto`, `parseHandshakeMaybe`; `src/proto/quic_conn.zig` `pumpCryptoToHandshake` |
| A2 | Medium | **Post-quantum hybrid rarely negotiated.** The server preference is X25519, then P-256, then X25519MLKEM768. Chrome sends both X25519 and hybrid shares, so it gets classical X25519 and the PQ key exchange stays unused for real clients. QUIC behaves the same way. | `src/crypto/tls_server.zig:2267`, `:2334` |
| A3 | Medium-low | **No fault check in RSA-CRT signing.** `privateOp` returns a CRT signature without re-verifying `s^e ≡ m (mod n)`. One induced fault in a CRT branch leaks a prime factor (Bellcore). Base blinding is present, but it does not substitute for this check. It applies only to RSA certificates: the TLS 1.2 ServerKeyExchange and self-signed X.509. | `src/crypto/rsa_sign.zig` `privateOp` |
| A4 | Low | **Unverified outbound fetch in the live configs.** Both nodes set `news_insecure_tls = true`, so the weather/news feed shown to users can be tampered with by anyone on the network path. The code is correct; this is a config choice. | `[geo]` in both live configs |
| A5 | Low | **ECDSA private scalar not wiped.** In `armor genpkey -algorithm ec`, the scalar (`kp`, the by-value copy, and `priv`) is never wiped. The Ed25519 path does wipe. `ecdsa_p256.KeyPair` has no `deinit`. | `src/cli/pkey_cmd.zig` `generatePem`, `ecPrivateKeyDer` |
| A6 | Low | **HPKE DHKEM label deviates from RFC 9180.** The code uses `"dh"` instead of `"eae_prk"`. The tests document this. Onyx-to-Onyx ECH works, but standard ECH clients cannot interoperate. | `src/crypto/hpke.zig` `extractAndExpand` |
| A7 | Low | **Duplicate QUIC transport parameters accepted.** RFC 9000 §18.1 requires TRANSPORT_PARAMETER_ERROR; the code keeps the last value. | `src/proto/quic_transport_params.zig` `decode` |
| A8 | Low | **Our QUIC client skips connection-ID checks.** It does not compare `original_destination_connection_id` or `initial_source_connection_id`. The production server sends both correctly, so browsers can verify them; only our own client is affected, and it is not used in production. | `src/proto/quic_handshake.zig` `Client.parseEncryptedExtensions` |
| A9 | Info | **TLS 1.2 conformance gaps.** `record_size_limit` has no upper-bound check (the value is clamped where used). Trailing certificates in the client certificate list are ignored (certfp pins only the leaf). | `src/crypto/tls12_server.zig` |
| A10 | Info | **Misleadingly named verification bypass.** `skipServerCertVerifyForTest` is called from production `http_fetch` when operator config sets `insecure_skip_verify`. It is not reachable by an attacker, but the name hides a real production bypass. | `src/daemon/http_fetch/tls_exchange.zig` |

## Assurance gaps

- **The record-layer exploit corpus misses production.** `tls_record.sealRecord`
  and `openRecord`, the target of the tamper, truncation and overflow test
  corpus, have no callers outside `tls_record.zig`. Production TLS 1.3 seals and
  opens with its own inline AEAD dispatch in `tls_server.zig`. The local wrapper
  cannot even represent AES-128-GCM, which is the default suite.
- **`src/crypto/tls.zig` is not used in production.** Its generic key-schedule
  and handshake abstraction is used only by `tls_kat.zig` and `tls_props.zig`,
  so those tests prove properties of code that does not ship.
- **Wycheproof coverage is nominal.** `wycheproof_kat.zig` holds four
  hand-written cases; the JSON corpus is not imported. There are no ACVP vectors
  for AEAD, ECDH or ECDSA, and no independent known-answer test for X-Wing,
  X25519MLKEM768 in TLS, or the ECH seal.
- **Fuzzing misses whole engines.** The TLS 1.3 server and client state
  machines, QUIC and DTLS are not fuzzed end to end. Coverage-guided `--fuzz`
  crashes inside the toolchain's fuzzer runtime.
- **Interop testing is thin.** BoGo has 24 passing cases, mostly TLS 1.2. There
  is no OpenSSL or browser harness for TCP TLS.
- **The constant-time check is opt-in.** `zig build ct-check` is not part of
  `zig build test`. RSA bignum code is variable-time beneath its blinding.
- **Nothing validates the Helix nonce counter.** `aead.CounterNonce.resumeFrom`
  trusts the restored counter. Its safety rests on the Helix capsule
  round-tripping a monotonic counter.

## Feature inventory (summary)

**Live in production**

- TLS 1.3 by default; TLS 1.2 is opt-in, ECDHE-AEAD only, with Extended Master
  Secret required.
- Groups x25519, secp256r1 and X25519MLKEM768 (but see A2).
- Session tickets, and 0-RTT that is opt-in and guarded against replay
  in-process only.
- HelloRetryRequest; KeyUpdate with kTLS rekey.
- SNI with multiple certificates; OCSP stapling and must-staple.
- record_size_limit; mTLS with certfp pinning feeding SASL EXTERNAL; raw public
  keys.
- kTLS TX and RX for TLS 1.3, in all three suites.
- QUIC-TLS for WebTransport, with Retry and path migration.
- DTLS 1.2 and 1.3 with SRTP for media.
- ACME HTTP-01.
- Hot reload of the default certificate; the TLS 1.3 exporter used for
  SCRAM-PLUS.
- Middlebox compatibility mode.

**In the engine but not wired into the daemon**

- ALPN on the IRC listener, and RFC 8879 certificate compression.
- Delegated credentials: the server engine supports them, but nothing mints
  them.
- `signature_algorithms_cert` enforcement.
- The ECH client, ECH `retry_configs`, and the CT log list.

**Missing**

- GREASE, including ECH GREASE, and post-handshake auth.
- ECH with HRR or PSK, and `ech_outer_extensions`.
- In QUIC: HRR, 0-RTT, resumption and mTLS, stateless-reset sending, and key
  update for the SHA-384 suite.
- The TLS 1.2 exporter and kTLS for TLS 1.2.
- psk_ke and external PSKs.
- ML-DSA as a TLS signature scheme. ML-DSA and SLH-DSA certificates can be
  verified but not signed.
- ACME dns-01 and tls-alpn-01; the ACME account key is the certificate key.
- Hot reload of SNI and ECH material.
- In the `armor` CLI: live `s_client -connect`, `s_server` and `enc`.

**Operations**

- The only TLS metric is `onyx_tls_handshake_us`. There are no failure counters
  by reason, no kTLS, resumption or 0-RTT counters, and no OCSP-state or
  certificate-expiry metrics.
- Suite order, group order, ticket lifetime and the 0-RTT skew cannot be
  configured.

**Documentation drift**

- `[tls].tsumugi_max_meshpass_len` in crypto.md should be
  `mooring_max_meshpass_len`. That key, `tls.debug_log`, `tls.ratchet_max_skip`
  and `tls.treekem_max_members` are applied only in tests and do nothing in the
  daemon.
- The docs say ECH `retry_configs` are sent; they never are.
- `early_data_age_skew_ms` is documented as a TOML key but is not one.
- tls.md omits X25519MLKEM768 and cites RFC 5280 for HRR; it should be
  RFC 8446.
- Stale headers in `tls_server.zig` and `tls_certs.zig`.

## Roadmap

The phases are ordered by risk and then value. Each item names its acceptance
evidence.

### Phase 1: security fixes (next patch release)

1. **A1, cap QUIC handshake buffering.** Reject a declared handshake length
   above about 64 KiB in `parseHandshakeMaybe`, and cap `Server.recv` and the
   client's `recv_initial` and `recv_handshake`. *Acceptance:* a regression test
   that streams an in-order 16 MiB ClientHello and gets a typed error at the
   cap; the WebTransport browser smoke stays green.
2. **A2, prefer the PQ hybrid.** Order groups X25519MLKEM768, then X25519, then
   P-256 in the key-share choice and in the HRR list, for both TCP TLS and QUIC.
   *Acceptance:* a test where a ClientHello carrying both shares selects 0x11ec;
   a live Chrome connection shows the hybrid.
3. **A3, RSA-CRT fault check.** Verify `s^e mod n == m` before returning, and
   return a typed error on mismatch. *Acceptance:* a fault-injection test.
4. **A5, ECDSA key hygiene.** Add `ecdsa_p256` key wiping and use it in
   `genpkey`.
5. **A4, turn off insecure news TLS.** Supply a CA bundle, or move the feed to a
   provider with a verifiable certificate; set `news_insecure_tls = false` on
   both nodes. Rename `skipServerCertVerifyForTest` to
   `disableServerCertVerification` (A10).
6. **A7 and A9, conformance.** Reject duplicate QUIC transport parameters;
   enforce the `record_size_limit` upper bound in TLS 1.2.

### Phase 2: assurance (make the tests prove what ships)

1. Route production TLS 1.3 record protection through one audited
   implementation: either `tls_record.sealRecord` and `openRecord` extended to
   AES-128-GCM, or move the exploit corpus onto `tls_server`'s seal and open.
   Delete or merge `tls.zig`, or point its known-answer and property tests at the
   live engine.
2. Import the Wycheproof JSON corpora for AES-GCM, ChaCha20-Poly1305, X25519,
   ECDH-P256, ECDSA-P256, RSA-PSS and HKDF. Add known-answer tests for X-Wing
   (draft vectors), X25519MLKEM768 and ECH (draft vectors).
3. Fuzz the TLS 1.3 server and client engines end to end, plus QUIC Initial
   handling and DTLS. Fix or replace the broken coverage-guided `--fuzz` path.
4. Grow BoGo to cover the TLS 1.3 server. Add an OpenSSL `s_client`/`s_server`
   interop step and a headless-Chromium TCP TLS smoke to the release gate.
5. Run `ct-check` in CI. Add a monotonicity guard to the Helix nonce counter
   restore.

### Phase 3: wire up what the engine already has

1. Advertise ALPN on the IRC listener (`irc`, plus `h2` and `http/1.1` where
   relevant).
2. Send ECH `retry_configs`, and fix the HPKE label to RFC 9180 (A6). Gate that
   wire change behind a new ECH config version.
3. Add a TOML knob for certificate compression, and enforce
   `signature_algorithms_cert`.
4. Hot-reload SNI certificates and ECH keys on REHASH and ACME renewal.
5. Remove or wire the dead `[tls]` keys, and correct the documentation drift
   listed above.

### Phase 4: features

1. GREASE (RFC 8701) for cipher suites, groups, extensions and ECH, on both
   server and client.
2. ECH with HelloRetryRequest; `ech_outer_extensions`.
3. QUIC: HRR, resumption, 0-RTT with a replay guard, and stateless resets.
4. Delegated-credential minting (`armor dc mint`) with automatic short-lived
   rotation.
5. The TLS 1.2 RFC 5705 exporter (SCRAM-PLUS over 1.2) and kTLS for TLS 1.2.
6. ACME dns-01 and tls-alpn-01, with an account key separate from the
   certificate key.
7. A mesh-wide 0-RTT replay guard, so early data stays safe behind multiple
   nodes.
8. `armor` CLI: live `s_client -connect`, `s_server`, an ECH config generator
   and an OCSP fetch.
9. Later: an ML-DSA TLS signature scheme and certificates, once the browser and
   CA ecosystem supports them.

### Phase 5: operations

1. TLS metrics: handshake failures by reason, version, suite and group,
   resumption and 0-RTT acceptance, kTLS active, OCSP staple age and status, and
   days until certificate expiry (alert even when ACME is off).
2. Config knobs for group and suite order and for ticket lifetime, with safe
   defaults.
