## 1. Release thesis

**0.7 is the release where Onyx Server's performance story becomes measurable and its
hot-upgrade path becomes version-safe — and where we deliberately decline the two
optimizations that would put both at risk.**

The audit behind this plan started from a hypothesis that turned out to be wrong, and the
correction is the most valuable thing in this document. The hypothesis was that the
daemon's biggest performance wins were already written and merely *unwired*: a modern
io_uring backend with multishot receive, provided-buffer rings, and a runtime capability
probe sits at `src/substrate/io/ring.zig` with no importer outside its own directory,
while the hot path runs a thinner inline ring at `src/daemon/server.zig:860` with feature
flags defaulted false. Both halves of that observation are true. The conclusion drawn from
them was not.

Adversarial review against live source established that the substrate ring is **less**
capable than the shadow it would replace, not more: its `OpKind` has five variants
(`src/substrate/io/ring.zig:120-126`) where the daemon needs seven — it has no `.connect`
for S2S dials (`server.zig:1051`), no `.poll` for the cross-reactor wake eventfd
(`server.zig:1086`), and no cancel op at all, which makes the entire Helix quiesce protocol
(`server.zig:7558-7652`) unimplementable on it. The promised runtime probe does not exist —
`ring.zig:98` is `narrow()`, a pure function over capabilities someone else measured. Its
provided-buffer pool is largely a model: `registerAll` (`src/substrate/io/buf_ring.zig:142`)
flips a bool and fills an in-process array without ever registering with the kernel. And
its accept passes flags `0` (`ring.zig:361`) where the shadow passes `posix.SOCK.CLOEXEC`
behind a ten-line comment (`server.zig:1035-1044`) explaining that omitting it strands a
re-exec'd meshed node's peer link into split-brain. Adopting it wholesale would reintroduce
a bug the project already paid for.

More consequentially, **multishot receive and provided-buffer rings are not a config key —
they are a rewrite of the buffer-ownership protocol that Helix USR2 is built on.**
`handleRecv` (`server.zig:9501`) clears `conn.recv_armed` unconditionally at `:9505` and
never reads `event.more`; the only production consumer of `.more` in the file is
`handleAccept` at `:8010`. Under multishot the original SQE stays live, so the re-arm at
`:9582` submits a second kernel writer into the same `conn.recv_buf`. `ownedSocketIoQuiesced`
then reports quiesced while the kernel still holds a write reference, `performUpgrade`
execve's, and the kernel writes into a page the successor owns — silent corruption, not a
crash, and invisible to the suite because every test constructs completions with
`.more = false`. Separately, `if (event.res <= 0) conn.closing = true;` (`:9566`) turns a
provided-buffer `-ENOBUFS` into a shard-wide disconnect under exactly the burst load the
work is meant to serve.

So 0.7 takes the wins that do not touch buffer ownership, and defers the two that do.
`defer_taskrun` + `SINGLE_ISSUER` and `sqpoll` are the only flags the shadow ring's
`setupFlags` (`server.zig:877-885`) actually honors today — everything else is discarded at
`_ = self.features;` (`:1031`). Those, plus `cqe_batch` tuning, are real and safe. The
larger unrealized win is concurrency, not flags: multi-reactor sharding genuinely runs
(see [§6.4](#64-correction-to-the-adversarial-review-sharding)), but production has never
been driven past one shard with a seeded simulation over the reactor-zero timer guards.

**What a user sees at 0.7:** a node that hot-upgrades cleanly from 0.5.8, measurable
throughput gains backed by a reproducible benchmark rather than an assertion, an
operator-queryable anti-abuse and mesh-health surface, and a hardening story with an
enumerated corpus behind it.

### 3.2 Recommendation: `0.5.8` → `0.7.0`

Skipping `0.6` is defensible and cheap. The bump itself is **cosmetically safe**, and this
was verified rather than assumed:

- `src/proto/semver.zig` has a full parser and comparator with **zero functional
  consumers** — the only references are the re-export at `src/proto/root.zig:276` and a
  `_ = semver;` discard at `:632`. Nothing in the daemon parses or compares the release
  version.
- `server_version` (`server.zig:620`) flows into 002/004/351/MOTD/CTCP as an opaque string.
  The banner test concatenates `server_version` itself, so it auto-follows.
- Helix capsule compatibility is per-schema `u16` (`src/daemon/helix/capsule.zig:100-118`),
  and the Mooring handshake is `protocol_version: u16 = 1`. Both are independent of the
  release semver.
- A `-rc.1` prerelease is safe: `gitCommit` already appends `-dirty` (`build.zig:930-931`),
  so a hyphen in the composed string is an existing, exercised case.

**The version number is not the upgrade hazard.** See [§9 R-1](#9-risks-severity-tagged) —
the real gate is an exact-string capability token, and that is what P0-0 addresses.

**Sequence:** bump `build.zig.zon` to `0.7.0-rc.1` at the start of the stabilization phase;
promote to `0.7.0` at tag. Fix `README.md`, `packaging/README.md`, and backfill `NEWS.md`
for `0.5.7`/`0.5.8` as part of P1-6 so the release notes are contiguous.

## 5. Out of scope for 0.7

Named explicitly so they are declined on purpose rather than missed.

Windows/BSD I/O, IRCX expansion, client IRCX UI, and the harden hunt are **in
scope** for this same 0.7 tag — see [`0.7-MAJOR-ROADMAP.md`](0.7-MAJOR-ROADMAP.md).
The items below stay declined even for the major 0.7:

- **Multishot receive.** Requires a `.more`-aware `handleRecv` and a quiesce predicate that
  can express kernel-held write references. Deferred past 0.7. (R-3)
- **Provided-buffer rings (`buf_ring`).** Requires a real `IORING_REGISTER_PBUF_RING` path,
  a `buffer_id` field on `RecvEvent` (absent today at `server.zig:947-951`), a decoder that
  reads from the ring rather than `conn.recv_buf` (`:9569`), and an `-ENOBUFS` path that
  re-arms instead of closing (`:9566`). Deferred past 0.7. (R-3)
- **Zero-copy send (`send_zc`).** Same ownership class; no independent justification yet.
- **Decomposing `server.zig`.** 102,152 lines, 1,496 methods, 712 in-file tests including
  the exploit cases. The reactor-zero guards are file-private and load-bearing, and Helix
  reaches directly into `ConnState` privates (`quiesceOwnedSocketIo` at `:7558`,
  `sealSecuredLink` asserting six latches at `:7709-7712`). With no decomposition verifier
  in the tree, a mechanical split is a hand-audit of the most dangerous file in the project.
  If wanted, 0.8 as its own train with nothing else in flight, gated on P0-3.
- **Adopting `src/substrate/io/ring.zig` as the daemon backend.** Strictly less capable than
  the shadow ring (see §1). P1-5 decides its fate instead.
- **Any capsule schema bump not required by P0.** Each one trips the capability gate (R-2).

  **Landed** as `zig build bench` (`src/substrate/bench.zig`, `tools/bench.sh`), built

  kept out of `zig build test` and `all-checks`. See [`../dev/benchmarks.md`](../dev/benchmarks.md).
- DST exists (`src/substrate/sim.zig`, `src/substrate/fault_loom.zig`) with no dedicated
  build step. P0-3 gives it one.
- **Gate inventory.** Of the gates this plan cites, `check`, `test`, `test-server`,
  `test-helix`, `test-tls`, `test-exploit`, `test-attack`, `test-mesh`, `test-ircx`, and
  `test-media` all exist today. `bench` and `test-dst` do **not** — they are deliverables of
  P0-1 and P0-3 respectively, not commands anyone can run now. (`bench` has since landed;
  `test-dst` is still outstanding.)
- The config surface exposes **two** io keys, `io.ring_entries` *and* `io.cqe_batch`
  (`src/daemon/config_format.zig:1334-1335`). An earlier draft of this plan named only the
  first.

### 6.4 Correction to the adversarial review: sharding

The review asserted that `runThreaded` "still clamps to 1," which would have made the
multi-shard performance story fiction. **This was checked and it is wrong.**
`runThreaded` (`server.zig:7457`) branches: `if (self.reactors.len <= 1)` runs the loop
inline on the calling thread; otherwise it stands up the cross-shard fabric and calls
`self.pool.start(self.reactors.len, ...)`, with `reactorWorker` binding
`current_reactor = &self.reactors[shard]` per thread. The reactor array is sized by
`clampShards(config)` (`:4466`), which clamps to `[1, shard.max_shards]`. Multi-reactor
genuinely runs; the single-reactor fallbacks are graceful degradation on fabric-init or
pool-spawn failure, not a clamp.

The review almost certainly read the stale comment at `:1897-1901` rather than the function
body — which is precisely why §6.2 is a P0-6 deliverable and not cosmetic. The real gap is
that production has never been *driven* past one shard with a seeded simulation, which is
P0-3.

## 9. Risks (severity-tagged)

| ID | Sev | Risk | Mitigation | Owner |
| --- | --- | --- | --- | --- |
| **R-1** | **CRITICAL** | **Hot-upgrade refused for the whole deployed fleet.** `hasUpgradeCapabilityLine` (`helix/live.zig:312-314`) demands a **byte-identical full line**, and `probeUpgradeExecutableFd` (`:321-347`) is run by the **predecessor** against **its own compiled-in** token. A deployed 0.5.8 probing a 0.7 binary demands 0.7 print 0.5.8's exact token. Any 0.7 capability change fails the match, `openCompatibleUpgradeTarget` returns `error.UpgradeTargetIncompatible`, and UPGRADE is refused. It fails *closed* — correct — but the operator's only remaining path is a hard restart, dropping every live session. That is precisely the mass-disconnect Helix exists to prevent. The existing `predecessor_v3` bridge does **not** cover it: v3 lacks `sessions-v4`. | **P0-0**, landed first. | zig-coder |
| **R-2** | **HIGH** | **`ConnState` changes cascade into R-1.** The `clients` capsule is pinned `current = min = max = 5` (`capsule.zig:134`) with an explicit "cold-refuses instead of degrading" contract. Any change to what a carried connection holds forces a capsule bump → capability change → R-1. Perf work on recv/send buffers is exactly that class of change. | P1-3 gated on P0-0; prefer memory wins that leave carried shape identical. | onyx-server-perf, onyx-server-helix-reviewer |
| **R-3** | **HIGH** | **Multishot/buf_ring would silently corrupt the successor.** `handleRecv` ignores `event.more`, so multishot double-arms the kernel onto `conn.recv_buf` while `recv_armed` reads false; quiesce reports clean and `performUpgrade` execve's under a live kernel write reference. Invisible to the suite — every test builds `.more = false`. | **Out of scope** for 0.7 (§5). Revisit in 0.8 behind a redesigned quiesce predicate. | — (deferred) |
| **R-4** | MEDIUM | Performance claims remain unfalsifiable if P0-1 slips, and the failure modes of any I/O change only appear under sustained load that no harness can currently generate. | P0-1 is Phase 1 and blocks P0-2. | onyx-server-perf |
| **R-5** | MEDIUM | Multi-reactor timer guards pass vacuously at `count == 1`, so a dropped or inverted guard reproduces the roster-decay bug with the entire suite green. | P0-3. | onyx-server-dst, onyx-server-reactor |
| **R-6** | LOW | Substrate ring left in the tree looking production-ready invites a future contributor to adopt it and reintroduce the accept-CLOEXEC split-brain bug. | P1-5. | onyx-server-reactor |
